# M1-04 顧問追問與接續對話驗證

日期：2026-11-05

唯一驗收規格為 [Issue #13](https://github.com/backtrue/realtime-black/issues/13)：先只說「廣告沒訂單」，同一通補充產品、目標與數據，再與資訊完整的案例比較，最後由小黑本人試聽

## 來源與環境

語音 source `ee533fb2b384597a9af158d0d6988a5cb2dc2bff`，實際模型 gpt-realtime-2.1、marin 音色。載入目前的 OpenAiRealtime、MemberEngine、DefaultMethods，透過本機原生 Workers 的 CallMethods 讀取實際 MCP 套件。會員與儲存使用合成 fixture，沒有使用正式會員額度或個人 MCP OAuth，未使用麥克風與保存音檔

## 實際對話對照

| 案例 | 實際結果 |
|---|---|
| 只說「廣告沒訂單」 | 先問是有點擊／到站但不成交，還是曝光／流量不足，沒有直接判定原因 |
| 同一通補充商品、受眾、目標、同週 1000 到站／200 加購／2 訂單、追蹤未驗證與每週 4 小時 | 接續檢查加購後至付款的落差，要求核對資料期間、來源與事件；把運費、價格與系統問題保留為待驗證原因，依可取得證據排順序 |
| 一開始就給完整資料 | 直接進入追蹤口徑、付款與錯誤證據、結帳流程的順序，說明未知資料及每週 4 小時的安排，沒有重問已提供的商品與數字 |

兩組均實際讀取 E03 與 MK-453 全文，18,972 bytes、SHA-256 `6e778afe85d29536369790d80aedec25392a5563d4290716839816e9b81b6cfe` 重新計算一致。補充案例另讀取方法引用的共用規則。實際語音 RTP 封包均大於零、最後回應狀態為 completed，提供者通話已確認結束，方法 runtime 已清理

首次完整案例在測試 max_output_tokens=2048 時回應為 incomplete，原逐字與失敗狀態保留。該案例以 4096 單獨重測後回 completed；產品指示與模型設定沿用原來源，未重跑已通過的補充案例

原始輸入、完整回覆、工具順序、方法 SHA、重測與清理見 [去識別證據](examples/consultant-validation-2026-11-05.json)。本人試聽及教學口吻意見尚待完成，Issue #13 保持開啟
